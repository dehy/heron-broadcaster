# M15 – Encrypted and tested backups

**Depends on:** M12.

## Why

A backup holds every secret of the station: output and stream server passwords, webhook secrets, the AcoustID key, password and token hashes. M12 writes it readable by the API's user only, and asks for copies off the machine: on a share, in a synchronized folder, downloaded. There, file permissions no longer protect anything. Encrypted with a key that only the station's admins hold, a backup can go anywhere.

And a backup that was never read back is only a hope: a dump cut short, a file damaged on a share or a lost key show up the day a restore is needed. Design: [Backups – Encryption](../backups.md#encryption), [Testing backups](../backups.md#testing-backups).

## Scope

- **Encryption with [age](https://age-encryption.org)**, a standard file format (X25519, ChaCha20-Poly1305), readable with the `age` and `rage` command-line tools: both files of every backup, `….json.age` and `….sql.gz.age`.
- **Heron keeps only the public key.** It encrypts every backup with it, daily ones included, and cannot decrypt any of them by itself: a restore asks for the key.
- **The key** is generated by Heron, shown once with a file to download, and typed back before encryption is turned on. An admin who has their own age key gives its public key instead.
- **Optional:** off until an admin sets a key. Until then, admins see a banner saying backups are not encrypted.
- **Turning it on encrypts the backups already in the folder**, then takes a backup.
- **Changing the key:** new backups use the new key; the list shows which backups need an earlier one. **Turning it off:** new backups are written in clear again.
- **Regular checks, per admin:** Heron asks each admin to type the key back after 1, 3, 7 and 14 days, then every 30 days, so a lost key is noticed before a restore needs it.
- **Restore with the key:** from the Backups page, from the API, with `heron-api backup restore --key-file`. A configuration file in clear (an older backup) is still accepted.
- **The encryption setting and the checks are not in the configuration file**, and a restore does not change them.
- **Every backup checked as it is written:** the configuration file read back and checked as a restore would, the dump whole (`-- Dump completed`), the checksums of both files written next to them (`sha256sum` format) and checked every day: a file missing, cut short or changed is marked damaged.
- **A test read with the key:** each key check also decrypts the newest backup encrypted with that key, checks its configuration file and reads its dump to the end, without writing or restoring anything. *Test* does the same for any backup. Backups in clear are tested without a key, each daily one as soon as it is taken.
- **The last test on the Backups page**, a banner when it failed or when none has passed for 30 days, and metrics for the last backup and the last test that passed.
- **A restore drill, documented:** a second Heron, without its engine, the dump and the configuration file restored into it.

## Out of scope

- Passphrases chosen by the user: a key derived from a passphrase can be guessed offline from a stolen backup.
- Several keys at once (several recipients), hardware keys and age plugins.
- Encrypting older backups again with a new key: Heron cannot read them.
- Decrypting in the browser, downloading a backup decrypted.
- Recovering a lost key: there is none, by design.
- Encrypting the database, the library or the secrets inside Heron's database.
- Restoring into a database automatically to test a backup: that is the drill, by hand.
- Checking copies of the backups outside the backup folder.

## Deliverables

- `heron-api`:
  - age encryption of both files, the dump streamed through it;
  - the `backup_encryption` setting, left out of the configuration file and of restores;
  - the routes under `/api/v1/backups/key`, and the key on restores;
  - the checks per admin, and `GET /backups/state` for the banners;
  - the checks of each backup as it is written, the checksums file and the daily check, the test read, the `backup_tests` setting and the metrics;
  - `heron-api backup restore --key-file`.
- `heron-web`:
  - the encryption card on the Backups page: set, check, change or turn off the key;
  - the key on restores, with the public key it must match wherever a key is typed;
  - the "not encrypted", "damaged" and "not tested" banners, and the check dialog;
  - *Test* on each backup, and the last test.
- CI: `scripts/check-two-stations.sh` restores an encrypted backup.

## Acceptance criteria

- [x] With encryption on, both files of a daily, manual, before-restore and uploaded backup are age files. `age -d -i` with the key decrypts them into the same configuration file and dump as without encryption, and the documented commands restore the dump.
- [x] Nothing Heron stores (database, settings, logs, backup folder) holds the secret key. No route returns it after it is generated.
- [x] Encryption is turned on only after the key is typed back. Every backup already in the folder is then encrypted, and a backup is taken.
- [x] A listed or uploaded backup restores with its key, from the web UI, the API and the command line. A wrong key, or none, is refused with a clear message and changes nothing. A tampered file is refused. A configuration file in clear is still restored.
- [x] Restoring a backup taken before the key changed, or before encryption was turned on, keeps the current key, keeps encryption on or off as it is, and keeps every admin's checks.
- [x] After a key change, the list shows the backups that need an earlier key, and new backups use the new one.
- [x] Wherever a key is typed (typed back, a check, a restore or a test of a listed backup), the public key it must match is shown; the generated key is shown with its public key.
- [x] Each admin is asked to check the key at the documented intervals. A correct key moves their next check further away; *Later* asks again the next day. A key change asks every other admin at once.
- [x] While encryption is off, admins see the "not encrypted" banner; other roles do not.
- [x] Only admins can set, check, change or turn off the key.
- [x] A configuration file a restore would refuse, or a dump cut short (the `mariadb-dump` process killed), fails the backup, as reported on the Backups page.
- [x] `sha256sum -c` passes on every backup's checksums file. A backup file deleted, truncated or changed in the folder is marked damaged at the next daily check, with a banner for admins.
- [x] Checking the key tests the newest backup encrypted with it: a good backup passes; a backup whose files were changed fails, saying which file. *Test* on an older backup passes with its own key and fails with another. Nothing is written to the database or the folder by a test.
- [x] The Backups page shows the last test. Admins see a banner when it failed, or when no test has passed for 30 days. The metrics give the time of the last backup and of the last test that passed.
- [x] The restore drill, followed as documented next to a running station, restores a backup into a second Heron without touching the station: it keeps streaming, its library and its stream servers untouched.
- [x] The engines play on through encrypting the folder, a backup, a test and a restore.
