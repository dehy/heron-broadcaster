# M15 – Encrypted backups

**Depends on:** M12.

## Why

A backup holds every secret of the station: output and stream server passwords, webhook secrets, the AcoustID key, password and token hashes. M12 writes it readable by the API's user only, and asks for copies off the machine: on a share, in a synchronized folder, downloaded. There, file permissions no longer protect anything. Encrypted with a key that only the station's admins hold, a backup can go anywhere. Design: [Backups – Encryption](../backups.md#encryption).

## Scope

- **Encryption with [age](https://age-encryption.org)**, a standard file format (X25519, ChaCha20-Poly1305), readable with the `age` and `rage` command-line tools: both files of every backup, `….json.age` and `….sql.gz.age`.
- **Heron keeps only the public key.** It encrypts every backup with it, daily ones included, and cannot decrypt any of them by itself: a restore asks for the key.
- **The key** is generated by Heron, shown once with a file to download, and typed back before encryption is turned on. An admin who has their own age key gives its public key instead.
- **Optional:** off until an admin sets a key. Until then, admins see a banner saying backups are not encrypted.
- **Turning it on encrypts the backups already in the folder**, then takes a backup.
- **Changing the key:** new backups use the new key; the list shows which backups need an earlier one. **Turning it off:** new backups are written in clear again.
- **Regular checks, per admin:** Heron asks each admin to type the key back after 1, 3, 7 and 14 days, then every 30 days, so a lost key is noticed before a restore needs it.
- **Restore with the key:** from the Backups page, from the API, with `heron-api backup restore --key-file`. A configuration file in clear (an older backup) is still accepted.
- **The encryption setting and the checks are not in the configuration file**, and a restore does not change them.

## Out of scope

- Passphrases chosen by the user: a key derived from a passphrase can be guessed offline from a stolen backup.
- Several keys at once (several recipients), hardware keys and age plugins.
- Encrypting older backups again with a new key: Heron cannot read them.
- Decrypting in the browser, downloading a backup decrypted.
- Recovering a lost key: there is none, by design.
- Encrypting the database, the library or the secrets inside Heron's database.

## Deliverables

- `heron-api`:
  - age encryption of both files, the dump streamed through it;
  - the `backup_encryption` setting, left out of the configuration file and of restores;
  - the routes under `/api/v1/backups/key`, and the key on restores;
  - the checks per admin, and `backups` in `GET /auth/me`;
  - `heron-api backup restore --key-file`.
- `heron-web`:
  - the encryption card on the Backups page: set, check, change or turn off the key;
  - the key on restores;
  - the "not encrypted" banner, and the check dialog.
- CI: `scripts/check-two-stations.sh` restores an encrypted backup.
- Docs: [Backups](../backups.md#encryption), [API](../api.md), [Data model](../data-model.md), [Web UI](../web.md#pages), [Architecture](../architecture.md), [Locked decisions](../decisions.md), the README.

## Acceptance criteria

- [ ] With encryption on, both files of a daily, manual, before-restore and uploaded backup are age files. `age -d -i` with the key decrypts them into the same configuration file and dump as without encryption, and the documented commands restore the dump.
- [ ] Nothing Heron stores (database, settings, logs, backup folder) holds the secret key. No route returns it after it is generated.
- [ ] Encryption is turned on only after the key is typed back. Every backup already in the folder is then encrypted, and a backup is taken.
- [ ] A listed or uploaded backup restores with its key, from the web UI, the API and the command line. A wrong key, or none, is refused with a clear message and changes nothing. A tampered file is refused. A configuration file in clear is still restored.
- [ ] Restoring a backup taken before the key changed, or before encryption was turned on, keeps the current key, keeps encryption on or off as it is, and keeps every admin's checks.
- [ ] After a key change, the list shows the backups that need an earlier key, and new backups use the new one.
- [ ] Each admin is asked to check the key at the documented intervals. A correct key moves their next check further away; *Later* asks again the next day. A key change asks every other admin at once.
- [ ] While encryption is off, admins see the "not encrypted" banner; other roles do not.
- [ ] Only admins can set, check, change or turn off the key.
- [ ] The engines play on through encrypting the folder, a backup and a restore.
